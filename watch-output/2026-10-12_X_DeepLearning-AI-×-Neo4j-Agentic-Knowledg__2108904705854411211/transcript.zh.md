[00:00] 這門課與 Neo4j 合作：你會設計一個多代理（multi-agent）系統，把結構化與非結構化資料轉成知識圖譜。主持人認為知識圖譜特別適合重視資訊準確度的高風險應用，課程會說明原因，也提供建置工具。
[00:22] 講師是 Neo4j 的生成式 AI 開發者布道師 Andreas Kollegger。
[00:35] 知識圖譜和 RAG 類似：先把文件切成片段、存進向量資料庫；不同的是，它還把片段放進圖形結構，並連結到從片段中抽出的實體（例如商品評論片段裡的商品、訂單、配送問題、瑕疵），實體與片段之間以「邊」表示關係。檢索時，實體會連同相關片段一起取回，讓 LLM 得到更精準的上下文；圖也能再連接從 CSV 等結構化資料建立的另一張圖。
[01:43] 要把兩類資料轉成知識圖譜，必須先決定圖的結構（schema）：有哪些類型的實體／節點、彼此有什麼關係。本課程不是靠人看資料決定，而是用 Google 的 ADK（Agent Development Kit）設計多代理系統，一次建一個代理：先與使用者對話釐清目標與圖的類型，再由一組代理處理結構化資料、另一組處理非結構化資料，最後由一組代理把兩邊的模型接起來並建圖。
[02:38] 感謝 Neo4j 與 deeplearning.ai 參與製作的人員。第一堂課會介紹知識圖譜的底層結構，以及如何用它找出產品問題的根本原因。
[03:13] 知識圖譜是什麼？先回頭看關聯式資料庫：人表、商品表，中間用「關聯表」連接。問「某人買過哪些商品」要做兩次 join；問「誰也買過同樣的商品」要再 join 回來；若要「推薦他下一個該買什麼」（找買過類似商品的人，再找出他們買過而此人沒買過的商品），join 愈來愈多、愈難讀。
[05:15] 改成圖：丟掉無關的紀錄，把關聯表的列變成直接連接人與商品的箭頭，重新排列後就一目了然。
[06:04] 這可以改寫成圖形樣式比對，用查詢語言 Cypher 描述（有點像具備樣式比對能力的 SQL）：圓括號是節點，帶冒號的箭頭是關係類型；先比對某人買過的商品，再延伸到也買過這些商品的其他人，再延伸到他們買的其他商品，並加上「否定樣式」，只留下此人沒買過的商品，作為推薦。
[08:09] 所以知識圖譜是把資訊表示成節點（人、商品、部落格…）與關係的資料庫；關係不是 join 表的慣例，而是資料庫中的一等公民，有語意、有方向、只有單一類型，節點與關係都能有鍵值屬性，節點可有多個標籤。Cypher 的寫法貼近自然語言，適合與生成式 AI 搭配，因為 LLM 擅長自然語言。
[09:16] 知識圖譜也方便把非結構化資料與結構化資料結合：文字切塊、做向量表示後同樣存進資料庫，就能同時使用向量相似度搜尋與樣式比對。
[09:37] 範例情境是根因分析：你是家具製造商，想了解客戶對產品的抱怨。要回答的問題包括：哪些產品問題最多？問題出在零件本身還是別處？若是設計問題交給設計團隊；若是製造或零件問題，則換零件或改善流程。做法是先問清楚目的（可能是供應鏈製造問題），再盤點可用資料：把產品連到供應商的物料清單（CSV）、以及從網路抓取的使用者評論。
[11:23] 目標資料模型：每個 CSV 變成圖中的節點或關係，構成「領域圖（domain graph）」；Markdown 檔切塊後成為「詞彙圖（lexical graph）」，代表原始文字及其結構；兩者之間以「主題圖（subject graph）」連接——從文字塊抽出的主題／實體（例如某使用者喜歡某張桌子，形成「主詞—謂詞—受詞」），若該桌子對應結構化資料中的產品，就能連到領域圖。最後得到由三個子圖組成的知識圖譜。
[13:41] 接著說明要設計的多代理系統。講師從工程角度把「代理（agent）」看成一種新的控制流程運算子：一個迴圈，裡面呼叫 LLM 決定要做什麼，再交給用戶端像 switch 那樣執行動作；智慧行為來自 LLM，執行仍透過程式碼。優點是有推理能力、可呼叫任何程式能做的工具、有記憶而能調適、只用自然語言提示就能上手；缺點是慢且貴（遠端 LLM 呼叫）、非確定性、正式環境中 token 成本會快速累積（講者主張）。多代理系統能改善其中一些缺點。
[15:20] 多代理系統是多個代理協作完成同一目標：有代理與子代理的階層、各自專精任務、可互相「委派」，有些代理被當成工具使用，且在轉換處可設與使用者互動的檢查點。圖中根代理可委派給代理 A 或 B，B 的某個工具其實是另一個代理。
[16:31] 本課程建構的是知識圖譜代理的一部分，聚焦在負責建圖的子代理：會學用 Google ADK 建代理、什麼是記憶與如何記錄關鍵資訊、如何定義工具，並把開放式對話收斂成可執行的程式碼。
[17:02] 架構由上而下：最上層是對話式代理，引導使用者了解流程但自己不做事；下一層有三個工作流程代理——結構化資料代理、非結構化資料代理，以及負責用建好的圖回答問題的 GraphRAG 代理。前兩者各自委派給負責各階段的子代理。
[18:20] 結構化資料流程：使用者意圖代理（釐清目標與要做的分析）→ 檔案建議代理（依目標從可用檔案挑出有用的，經使用者核可）→ 結構提案代理（由「提案者」與「批評者」兩個代理組成，反覆自我批評，產出符合使用者目標的圖結構），最終輸出稱為「圖建構計畫」，它不是圖本身，而是如何建圖的描述。
[20:37] 非結構化資料流程的前兩步相同（針對 Markdown 檔）；第三步不是依 CSV 設計結構，而是由兩個專門代理從文字中找出實體（人、地、事物）以及描述它們的事實，只描述「可以抽取什麼」而不做抽取，輸出稱為「知識抽取計畫」。
[22:01] 兩份計畫合在一起就是建圖規則；一個內含多個工具的單一工具會依規則迴圈建立領域圖、把 Markdown 切塊並做向量嵌入、抽取實體與事實，並連回結構化資料。第四到第八課會走完結構化流程、非結構化的實體與事實類型提案，以及第八課的建圖工具。
[22:51] 下一課開始寫程式：用 Google ADK 建第一個代理；已熟悉 ADK 的人可以跳過，但講師建議看一遍，了解他的實作想法。
[23:17] Lesson 3（Google ADK 介紹，第一部分）：先匯入 ADK 的 Agent、LiteLLM 封裝、記憶 session 服務與 Runner；用 LiteLLM 讓 ADK 呼叫 OpenAI（本課程使用 GPT-4o），並送出「are you ready?」測試連線。
[25:10] 再匯入把 Neo4j 與 ADK 結合的輔助函式庫：把查詢結果統一包成 ADK 偏好的 success／error 字典、轉成可序列化的格式，並以單一連線（singleton）提供 graphdb；用只回傳一個字串的簡單 Cypher 測試連線。
[28:01] 工具就是函式：Hello World 的 say_hello 接受人名、回傳 ADK 偏好的字典。docstring 很關鍵，會交給 LLM，讓它知道工具做什麼、參數與回傳。
[30:34] Cypher 以 $ 表示查詢參數；用參數而非字串串接，可避免使用者把惡意查詢當成值注入（講者以「惡意名字」示範）。
[31:35] 定義代理要有：名稱（可加版本以便除錯）、模型、description（讓其他代理知道何時該委派給它）、instruction（相當於系統提示，說明用途與如何使用工具）、工具清單。
[33:53] 執行代理需要執行環境：Runner 管理事件迴圈、LLM 呼叫、代理間的傳遞與協調，並可使用記憶服務（記憶體內或 Neo4j 等資料庫）。
[36:15] 本課手動建立：記憶體內的 session 服務、單一使用者／應用程式／session；把使用者訊息「Hello, I'm ABK」包成 ADK 的 Content（role 為 user、可含多個 parts），並預設一個「代理沒有回應」的最終回覆。
[38:02] 事件迴圈：以 run_async 逐一取出事件（可開詳細輸出看每個事件的作者），直到事件標記為最終回應就取出文字；若代理選擇「升級（escalate）」，代表子代理無法處理、交回上層。
[41:17] 為了重複使用，把上述流程包成輔助類別 agent caller，並用工廠函式 make_agent_caller 建立（講者偏好用工廠方法處理較複雜的建構），後續各課都會用到。
[43:27] 用 agent caller 跑一段兩句的對話（「Hello, I'm ABK」「I am excited」），完成友善的聊天代理；至此學會建立代理、給工具、建立執行環境，並在 notebook 中用腳本測試。
[44:47] Lesson 3 第二部分：建立多代理團隊——一個根代理（也稱協調者、orchestrator）加兩個子代理：問候代理（say_hello 工具）與道別代理（say_goodbye 工具，無參數、固定回覆）。
[47:35] 重點是為每個代理寫好 description 與 instruction：描述讓其他代理知道「何時該用這個代理」（委派），指示讓代理自己知道目的與工具；建好多代理系統後，多數時間會花在優化這些指示（回到傳統提示工程）；道別代理的指示還示範了少量範例（few-shot）：bye、goodbye、thanks bye、see you 都算道別。
[49:19] 根代理負責協調並委派：委派與呼叫工具類似，但整段對話歷史與對話控制權都會交給子代理。根代理沒有工具，只能閒聊或委派；指示中明確要求遇到問候或道別要交給對應子代理，而不是自己回答。
[51:17] 開啟詳細輸出後可看到：根代理收到「Hello, I'm ABK」後轉交給問候子代理，子代理呼叫 say_hello 並從訊息中抽出人名；下一句「thanks, bye」時，問候子代理自己判斷該轉給道別子代理，後者呼叫 say_goodbye，得到最終回應。這種逐事件的輸出對除錯代理互動很有用。
[55:33] 最後一個重要元件是記憶：session state 預設就是一個字典，ADK 會追蹤其變動並在各代理間（無論平行或循序）保持一致。互動方式有兩種：透過 tool context（工具被呼叫時多帶一個參數，可讀寫狀態；ADK 會自動注入最後一個名為 tool context 的參數），或用 output key 把代理的最終回應存進狀態。示範在記憶體內保存。
[58:03] 把兩個工具改成有狀態版本：say_hello_stateful 透過 tool context 把使用者名稱寫進 state；say_goodbye_stateful 雖然沒有參數，仍能從 state 讀出名稱（沒有則用預設值）；再建立有狀態的子代理與根代理。
[61:07] 測試：建立 caller 後先看 session 的初始狀態是空的；跑完「打招呼、道別」的對話後，最終狀態包含使用者名稱 ABK。
[62:44] 也可以在 notebook 裡開互動模式：若沒先報名字，LLM 會自己從訊息中猜一個名字（講者覺得好笑也不理想）；改說「my name is ABK」後，工具才正確更新記憶，之後道別也會帶上名字。
[63:58] Lesson 3 結語：你建了單一代理、再建了含兩個專長子代理與一個協調根代理的多代理系統，已準備好進入真正的代理式知識圖譜建構。課程總結：你學會如何建立把結構化與非結構化資料轉成知識圖譜的多代理系統、如何設定各專門代理（提示與工具）、以及代理間如何共享上下文。
