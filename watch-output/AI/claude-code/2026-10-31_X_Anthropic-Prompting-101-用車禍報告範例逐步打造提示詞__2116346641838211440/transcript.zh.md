# Anthropic Prompting 101：用車禍報告範例逐步打造提示詞（繁體中文中譯）

```
[00:00] 大家好，感謝今天來參加 Prompting 101。我是 Hannah，Anthropic Applied AI 團隊的成員；和我一起的是同樣在 Applied AI 團隊的 Christian。
[00:11] 今天我們會帶大家看一些提示詞（prompting）的最佳實務，並用一個真實情境，一起把提示詞一步步組出來。
[00:20] 先簡單說明什麼是提示工程：這就是我們與語言模型溝通、讓它做我們想做的事的方式，也就是替模型寫出清楚的指令、給它完成任務所需的脈絡，並思考如何安排這些資訊，以得到最好的結果。
[00:42] 這裡面有很多細節、很多不同的思考方式，而學習它最好的辦法就是實際去做。
[00:52] 所以今天我們走一個動手實作的情境，改編自我們合作過的一位真實客戶。我們修改了客戶實際的需求，但這是個很有意思的案例：分析圖片、從中取得事實資訊，再讓 Claude 對內容做出判斷。
[01:12] 圖片內容的語言我其實看不懂，但幸好 Christian 和 Claude 都懂，那就交給 Christian 說明情境與內容。
[01:21] 先設定場景：想像你在一家瑞典保險公司工作，每天處理車險理賠。你手上有兩份資料：左邊是一份車禍報告表，記錄事故發生前後的經過；另一份是人手繪製的事故現場草圖。
[01:56] 這兩份資料就是我們要交給 Claude 的內容。一開始，我們可以先把這兩樣直接丟進 console，看看會發生什麼事。
[02:05] 切到 console，這是 Anthropic 的 console，使用新的 Claude 4 Sonnet 模型，temperature 設為 0，並給很大的 max thinking budget，確保 Claude 的能力不受限制。
[02:27] 提示詞非常簡單，只交代 Claude 的任務：審閱一份車禍報告表，判斷事故經過與誰有過失。
[02:42] 用這個簡單提示詞直接執行，Claude 以為這是發生在瑞典某條常見街道上的滑雪事故。
[03:00] 這個誤會情有可原，因為我們的提示詞完全沒有交代這裡到底在發生什麼事。第一次猜測其實不算太糟，但我們仍有很多直覺可以放進 Claude 裡。
[03:17] 切回投影片：提示工程是一門反覆迭代、靠實證的科學。以這個例子來說，我們幾乎可以設一個測試案例，確保 Claude 明白這是車輛環境、與滑雪無關，並一步步改進提示詞，確保它真的處理了你想解決的問題。
[03:43] 為此，我們來看 Anthropic 內部如何拆解提示詞，以及我們建議大家怎麼做：先談好提示詞的結構。
[03:59] 你可能習慣與聊天機器人來回對話，但像這樣的任務通常是用 API，我們希望只送出一則訊息，就讓 Claude 一次把任務做對，不用來回修正。
[04:20] 我們建議的結構是：先在最前面寫任務描述，告訴 Claude 它的角色與今天要完成什麼任務。接著提供內容，在這個案例就是車禍表單與事故草圖；這是動態內容，也可能是從別的系統取回的資料。
[04:42] 然後給詳細指示，幾乎像是一份逐步清單，說明希望 Claude 如何完成任務、如何推理。可以再給一些範例：「收到這樣的內容時，這樣回應。」最後，通常建議重複任何對任務特別重要的事項，與 Claude 一起回顧並強調關鍵點，再請它開始工作。
[05:15] 這是更細的版本，共十個要點，接下來我們逐一走過，並在 console 裡把提示詞建起來。
[05:25] 先由 Christian 講任務脈絡（task context）與語氣脈絡（tone context）。剛才的示範裡，我們幾乎沒說明 Claude 面對的是什麼情境，它只好大量猜測；所以我們要拆解清楚，給更明確的指示，並讓它理解被要求的任務是什麼。
[05:57] 其次是加入語氣：重點是讓 Claude 保持事實、保持有把握。如果 Claude 看不懂眼前的內容，我們不希望它亂猜誤導我們；我們要的是關於誰有過失的判斷，盡可能清楚、有信心，否則就失去了目的。
[06:23] 回到 console，切到 V2。我先把資料呈現出來：這是車禍報告表，共有 17 個勾選框，說明事故經過，左右兩欄分別是 A 車與 B 車。目的是讓 Claude 讀懂這份人工填寫的資料，並與這張草圖互相印證；表單與草圖是同一情境的不同資料點。
[07:12] 在第二版裡，我加入更多資訊：這個 AI 系統是協助理賠人員審閱瑞典文的車禍報告表；說明那是人手畫的事故草圖；並要求沒有十足把握就不要下判斷。
[07:44] 執行後，Claude 能辨識出這是車禍而不是滑雪事故，也看出 A 車勾選第 1 格、B 車勾選第 12 格；往下看，它仍指出資訊不足、無法完全有把握判斷誰有過失。這正符合我們設定的任務：不要做沒有事實依據的主張，有把握才評估。
[08:26] 但關於表單本身（表單包含什麼）我們還缺很多資訊，最好的做法是把它加進系統提示詞，由 Hannah 接著說明。
[08:40] 下一項是背景資料、文件與圖片。我們其實很了解這份表單：它每次都一樣、結構不會變，只是填寫的內容會變。這正是適合放進系統提示詞的資訊，告訴 Claude 它會看到的表單結構。
[09:15] 這也很適合用 prompt caching，因為內容永遠相同。這能讓 Claude 不必每次初次看到表單時都花時間弄清楚它是什麼，並且因為事先知道要看什麼，讀表單的表現更好。
[09:37] 另一件事是提示詞裡資訊的組織方式。Claude 很喜歡結構與條理，所以我們建議遵循標準結構，也可以用一些工具幫助 Claude 理解資訊。這些在文件中都有很多範例，所以可以拍照，沒拍也沒關係，內容都在網路上。
[10:08] 可用分隔符號，例如 XML 標籤，Markdown 也很有用；但 XML 的好處是可以指明標籤裡面是什麼，例如「這是使用者偏好」，包在標籤內的就都與使用者偏好有關，也幫助 Claude 在提示詞後面回頭引用那些資訊。
[10:35] 回到 console 看第三版：使用者提示詞維持不變，但把表單資訊放進系統提示詞（也可以試別的放法）。我們告訴 Claude 這份表單的一切：這是瑞典車禍表單、語言是瑞典文、標題是什麼、有兩欄代表不同車輛、17 列各代表什麼意思。
[11:11] 先前執行時，Claude 是逐行讀來理解每一列的意義；現在這些資訊可以預先給它。我們也說明表單怎麼填寫：因為是人填的，不會完美，人們可能畫圈、塗鴉、沒有打 X，所以讀表單時要留意各種標記方式，也說明這份表單的用途與意義，希望幫助 Claude 更好地分析。
[11:54] 執行後，使用者提示詞與任務都沒變，但 Claude 花的時間更少，也比較不會一邊敘述表單是什麼，因為它已經知道，不必把這些資訊回報給我們。它列出所有勾選項目與草圖內容，也變得更有信心，認定依據這張圖與草圖，B 車有過失。
[12:42] 我們大概都同意，看圖和清單後確實是 B 車有過失，所以已有改進。
[12:51] 接下來談幾個這次沒有用到、但對提高提示詞效果很有幫助的項目。首先是範例（examples，few-shot），這是引導 Claude 非常有力的機制。想像有些真實事故對 Claude 很棘手，但憑你的人類直覺與人工標註資料能得出正確結論；你可以把這些資訊放進系統提示詞，用明確的範例呈現：要看的資料（可用 Base64 編碼的圖片）加上如何拆解、理解的說明。
[13:56] 這是突破 LLM 應用極限的關鍵：持續把應用推到極限，取得它哪裡出錯的回饋，再把案例加進系統提示詞，下次類似情況發生時就能參考範例。
[14:22] 這裡是範例寫法，同樣強調我們偏愛的 XML 結構；Claude 受過這種微調，效果很好。這次只是簡單示範所以沒有用；但若是替保險公司開發，實際會有數十甚至數百個不易判斷、處於灰色地帶的範例，讓 Claude 下次下判斷時有依據。
[14:55] 另一個這次沒用到的是對話歷史（conversation history），概念與範例相近，確保有足夠豐富的脈絡資訊，供 Claude 替你工作時使用。
[15:11] 在我們的案例裡，這不是面向使用者的應用，而是在後台運作：保險公司有自動化系統產生資料，最後由人類把關。若是更面向使用者的應用，有很長且相關的對話歷史，系統提示詞就是放進去的好位置，因為它能豐富 Claude 的工作脈絡；我們這次沒有這麼做。
[15:45] 接下來我們要組出提示詞的最後一部分：回頭提醒當下的任務，並提醒 Claude 應遵守的重要準則。這麼做的理由之一是防止幻覺：我們不希望 Claude 憑空捏造提示詞或資料裡沒有的細節。
[16:13] 如果 Claude 看不出哪個框被勾選，我們不希望它猜、或捏造某個框被勾的說法；如果草圖畫得太糟，連人也看不懂，我們希望 Claude 能直說。這些都會放進最後的提醒與收尾步驟。
[16:37] 例如提醒它「有十足把握才回答」，甚至要求它在做出事實主張時引用表單上看到的依據；比方要說「B 車右轉」，就要說「我知道這點，是因為第 2 格明確被勾選」，我們也可以給這類準則。
[16:56] 回到 console，看下一版提示詞：系統提示詞完全不變，包括表單背景與填寫方式；其他脈絡與角色也不變，只是加上一份詳細的任務清單，說明希望 Claude 如何分析。
[17:21] 我們在做這個示範與處理客戶案例時發現的關鍵是：Claude 分析資訊的順序非常重要，這和人類的做法類似。你大概不會先看草圖就想弄懂發生什麼，因為那只是一堆方框與線條，沒有額外脈絡根本不知道它代表什麼。
[17:43] 但若先讀表單，就能知道這是車禍、看到勾選框代表哪些車輛在特定時刻的狀況，再回頭理解草圖就容易多了。所以我們告訴 Claude：先看表單，非常仔細地看，確認哪些框被勾選、不要遺漏，替自己列出所見清單；有把握地取得事實資訊後，再看草圖，並把從表單學到的對事故的理解，與草圖對照，據此得出對整份表單的最終評估。
[18:41] 執行後可以看到一個行為：因為我要求仔細檢查表單，它把過程展示出來，逐一說明每個框有沒有被勾選。這是你做提示工程時會發現的現象：先前版本由 Claude 自己決定要說多少所見；這裡我要求仔細檢查每個框，它就真的逐框檢查，這可能不是我們最後想要的，之後可以調整。
[19:20] 它也依要求用 XML 標籤給出其他內容：表單分析、事故摘要、草圖分析，並繼續認定 B 車明顯有過失。在這個簡單例子裡看不出差別，但遇到更複雜的圖、更不清楚的表單時，這種逐步思考對做出正確評估影響很大。
[19:49] 回到投影片，接著由 Christian 說明最後一塊，讓它更貼近真實世界的任務。
[20:01] 謝謝。正如 Hannah 所說，我們已設定好場景，確保 Claude 以正確的方式替我們行動；在提示詞末尾還要加上簡單的準則或提醒，強化我們想要的結果，其中一個重要項目是輸出格式（output formatting）。
[20:21] 想像你是開發這個 LLM 應用的資料工程師，那些華麗的前言固然不錯，但最終你要的是把資訊存進 SQL 資料庫或其他儲存位置；Claude 為了給出判斷而產生的其餘內容，對應用並不必要，你要的是關鍵資訊。
[20:45] 切回 console，這裡加入了簡單的重要準則：再次強化我們想要 Claude 展現的行為，要求摘要清楚、簡潔、準確，並確保除了分析本身，沒有任何東西妨礙 Claude 的評估。最後在輸出格式上，我要求 Claude 把最終判定包在標籤裡，其他內容我的應用都會忽略，只看它實際的評估。這樣之後可用來做某種分析工具，或只要一個明確的判定。
[21:29] 執行後，過程與先前相同，但因為要求用更直接的方式整理發現，輸出簡潔許多；最後它把輸出包在 final verdict 的 XML 標籤裡。
[21:46] 所以在這次示範中，我們從一場「滑雪事故」，到第二版不太有把握的車禍輸出，再到現在格式嚴謹、有信心的輸出，可以在它周圍建起應用，真正協助例如汽車保險公司這類真實世界的場景。
[22:10] 最後切回投影片，另一種塑造 Claude 輸出的重要方式，是「替 Claude 把話說在前面」，也就是預填回應（prefill）。解析 XML 標籤固然不錯，但也許你想要結構化的 JSON，確保可序列化並用於後續呼叫；做法很簡單，要求 Claude 必須以特定格式開頭，例如左方括號，或像畫面上的 itinerary 這個 XML 標籤，在我們的案例也可以是 final verdict 標籤。
[22:56] 這是塑造 Claude 回應方式的好辦法，不需要前面的鋪陳；不過前言也很重要，它能確保 Claude 依我們想要的步驟推理。在我們的案例，只要包在 final verdict 裡再解析即可，但你也可以用預填。
[23:14] 最後還有一點：Claude 3.7，尤其是 Claude 4，都是混合推理模型，也就是可以使用延伸思考（extended thinking）。這值得強調，因為你可以把延伸思考當作提示工程的輔助。開啟後，Claude 有時間思考，有思考標籤與草稿區，好處是你可以分析那份思考過程，了解 Claude 如何處理資料。
[23:47] 就像剛才的勾選框，它會逐步推演事故經過；你可以把這些推理方式寫進系統提示詞，不僅更省 token，也能了解這些沒有我們直覺的智慧模型如何處理我們提供的資料，因此對於改進系統提示詞非常關鍵。
[24:14] 那麼，感謝大家今天到場。我們會在現場，有任何提示詞的問題歡迎來問。想進一步學習的話，一小時後有「面向智能體的提示詞」，現在則有 ClaudePlays Pokémon 的精彩示範，請不要離開。這場沒有時間問答，但我們整天都在，歡迎來找我們聊聊。謝謝大家！
```
