[04:52] 最重要的是，我們看到三種 token：輸入 token（我們送給模型的一切）、輸出 token（模型送回的一切，不只是最後的摘要，還包括工具呼叫、編輯、思考，模型做的全部），以及容器內的快取 token。
[05:21] 你可能會在價格頁認出這個分類，因為價格頁正是這樣排的：每個模型每個 token 的價格，並分成輸入、快取輸入與輸出幾欄。
[05:32] 我們快速看看為什麼它們定價差這麼多。先看輸入：我們送出任何東西，模型仍要處理每個輸入 token，但可以一次平行處理，而 GPU 非常擅長這件事，所以每個 token 的輸入價格相當便宜。
[05:49] 輸出就不同了，模型一次只寫一個 token。寫出看似簡單的「const x equals one」，它要對整個上下文做一次完整運算才能產生 const，接上後再做一次完整運算產生 x，再來是 equals，依此類推。所以每個輸出 token 背後的運算量大得多，這也是輸出是各類 token 中價格最高的原因。
[06:16] 然後是快取 token，最便宜的一種。請求的大部分每次都相同：每次來回我們只是附加到結尾，前面的部分模型在上一個請求已處理過，所以伺服器不把它當全新內容，而是保留上次建立的內部狀態，只對與上一個請求開始不同的地方做計算。這就是提示快取（prompt cache）。
[06:44] 前面相同的那一段稱為「前綴（prefix）」，也就是你看到的那個容器。它以一般輸入價格的一小部分被讀回。新的部分第一次付全價，從下個請求起就進入容器內。
[07:00] Claude Code 會自動幫你設定這一切，但老實說我認為快取是你最大的槓桿：看橫條，進去很多、出來很少，而且進去的幾乎都在容器內。所以在健康的工作階段中，大部分輸入是便宜的快取輸入。
[07:20] 你可以用 usage 檢查自己的工作階段：那裡有一行提示快取，會顯示你的輸入有多少來自快取。健康的工作階段中這個數字應該很高。
[07:32] 還有幾點要留意，因為剛才看到的是一串可以最佳化的東西：多少 token 進去、多少出來、多少被快取。還有一件事：運行這一切的模型，是否真的適合這個任務。因為模型要處理每一個 token，像 Opus 或 Fable 這樣較大的模型，每個 token 做的運算更多，所以更貴。這對很多任務很好，但你的任務可能不需要。
[08:05] 而且因為它適用於每個輸入與輸出 token，它會直接乘上我們接下來要談的一切。所以第一件要做對的事：不要在不需要的任務上跑最大的模型。
[08:19] 也要說清楚，小模型不是比較差的模型。我喜歡這樣想：Sonnet 是很好的通才，Opus 是專家，Fable 是見過別人沒見過的問題的專家型人才，Haiku 則像個快速助理。
[08:32] 能精確描述的編輯、機械性修改、或對已在上下文中的程式碼提問，用 Sonnet 就很適合，而且每個 token 便宜得多。但如果有細微的 bug 或陌生領域、你不確定發生什麼事，Opus 這位專家值得多付一點。不是每個任務都需要。
[08:56] 下一件事是給 Claude 正確的上下文，讓它需要更少的工具呼叫與來回就能弄清楚你要做什麼。一部分在你的提示裡，一部分在於擁有對的環境與對的 CLAUDE.md、skills。有個很小的做法：你可以直接把檔案加進提示，例如「修好 @utils.test.ts 裡失敗的測試」。這樣在請求送到模型之前，Claude Code 就已放入該檔內容，第一次讀檔的工具呼叫根本不會發生。對大型工作階段來說是小事，但我仍喜歡。
[09:36] 此外，也要確保上下文裡沒有你這個任務不需要的東西。在新的工作階段輸入 context 就能看到：系統提示、已載入的工具、你的 CLAUDE.md、每項用了多少 token、你的 skills 與 MCP。開始新工作階段前都值得做一下，檢查是否加了不必要的東西、提示能不能更精簡。
[10:09] 看過這些洞察後，有幾件事可以做。第一是 CLAUDE.md：不要放不適用於每個任務的內容。你可能會發現裡面有「做資料庫遷移時，做這、做這、做那」，但那不適用每個任務，卻在每個提示都被送出。這類內容通常應移到 skills。skill 的好處是，只有在模型判斷這個任務需要時才載入，預設只送名稱與說明；模型可依說明判斷「現在要做資料庫遷移，載入這個 skill 合理」。但如果你只是要改寫檔案、與資料庫遷移無關，預設就不該帶上它。所以 CLAUDE.md 通常只放適用於每個任務的東西。
[11:02] 第二，仍在 CLAUDE.md 裡：檢查你是否還需要這些資訊。模型進步很多，三個月前你得給模型的指示，現在可能已不適用。我們現在有一個 skill 叫 claude-api prompt-audit，會檢查你所有指示（CLAUDE.md、skills）是否對較新的模型仍然有效；若否，它會提出 diff 建議移除或調整。光這樣就能從輸入 token 中削掉一大塊。
[11:35] MCP 伺服器也是同樣的想法：你可能連了很多 MCP，但現在它們的完整工具定義是「按需載入」，所以閒置的伺服器相當便宜，但不是零。執行 /mcp，把這個工作階段沒用到的關掉，或改用 CLI（如 GitHub CLI、AWS CLI），Claude 直接執行，完全不必預先載入。
[11:59] 另一個會填滿橫條的是指令輸出：指令印出的內容會像 Claude 讀過的檔案一樣進入對話，並在該工作階段剩餘時間都留著。過大的輸出 Claude Code 已有處理：超過某個大小，它會把輸出寫入檔案，只在對話中放短預覽與路徑。但要留意低於那個門檻的輸出：一個為 400 個通過的測試各印一行的測試執行器，可能剛好低於上限，那 400 行就成了之後每個請求的一部分。只印失敗的「安靜」回報器則只佔一小部分。Claude 常會自己加安靜旗標，但可靠的做法是把你整天要跑的兩三個指令，照你實際執行的寫法放進 CLAUDE.md，例如用 npx 執行單一測試的指令加上 reporter 參數。一旦提交，就成為全團隊的設定；若某件事特別吵，就讓它在子代理中執行（稍後說明）。
[13:06] 有些情況你也會發現模型做得比預期更多：更多思考、工具呼叫、檔案編輯。例如你說「把按鈕改成綠色」，有時只改顏色，有時它會想理解你整個程式碼庫與設計系統。這大多與 effort（投入程度）有關。effort 隨請求一起送出，告訴模型在宣告完成前要多徹底。
[13:36] 我們預設的值通常就好，但我也理解人們會因為在乎任務而想開到 extra high 或 max，這其實不一定必要。更高的 effort 代表更多輸出 token，進而也帶來更多輸入 token 等。我們看到像 Fable 5.1 這樣較大的模型，medium 就很出色，雖然名字聽起來不像，但足夠完成你的任務；較低的 effort 有時和前代模型的高 effort 一樣好。
[14:12] 這也給你一個經驗法則：結果不如預期時，是它「不夠懂」還是「不夠努力」？如果是不夠懂，那是模型的問題，也許該升級模型；如果它漏了檔案、偷懶、沒跑測試或做到一半就停，那是 effort 的問題。反過來，如果你發現它做太多，就調低 effort。
[14:34] 接著在談快取之前，再說一件關於 token 量的事：模型只會往你的上下文「新增」，從不移除。所以在長工作階段中，我們到目前為止談過的一切，每個請求都還在。雖然大多是快取的，但快取不是零，模型仍在處理它，而且大多時候你已不需要。
[14:57] 看這裡：上排是我在任務之間執行 clear，所以每個任務都從小的開始；下排是一個長工作階段，每一欄都還背著前一個任務，而且越來越高。下排用掉的 token 是上排的兩倍，只因為任務二和三一直在背著任務一。
[15:19] 你可以做幾件事。第一是 compaction（壓縮）：執行 compact，會用一份摘要取代整段對話；順帶一提，你也可以給它提示，說明要記住什麼、優先保留什麼。你可以用 rewind 丟掉最近幾輪，開始新工作時用 clear。若你覺得之後可能想找回舊對話，可以先重新命名該工作階段，再 clear，之後還能 resume 那個舊工作階段。
[15:51] 回到前面談過的快取前綴：要記得，伺服器只能重用與上一個請求「從第一個 token 起完全相同」的部分。這段相同的前面部分稱為前綴。但只要有一個 token 不同，那一點之後的所有內容對伺服器都是新的，並以全價處理。
[16:14] 這點與 compact 和 clear 有關：我們改變了前綴，這無可避免，因為我們改變了通往這一點之前的一切，所以會破壞快取，下一個請求你要為裡面的內容付全價。compact 之後那只是一份小摘要，所以通常沒問題。
[16:32] 前綴裡的其他東西也值得知道：它包括工具定義與系統提示；系統提示包含你的工作目錄與工作階段開始時的 Git 狀態快照，然後是你的 CLAUDE.md，再來是到目前為止的對話。這也是為什麼在工作階段中途換模型會發生同樣的事：快取是該模型自己的內部狀態，另一個模型沒有可重用的東西，只能把你整段對話重新讀一次。
[17:00] 在大多數模型上，改變 effort 等級也一樣，因為它同樣位於請求的前面（Fable 5.1 是例外）；你更改 effort 時會破壞提示快取。我們多半會在發生前警告你：快取還熱時你執行 model 或 effort，Claude Code 會先請你確認。
[17:19] 也有很多事中途改變完全沒問題，例如編輯檔案、更改權限模式，這些都在 Claude Code 這一側，不會碰到你的請求。你的 CLAUDE.md 只在工作階段開始時讀一次，所以中途編輯不會有任何變化，要到下個工作階段或 clear 之後才生效。
[17:38] 接著是時間，因為我們不會永遠快取。伺服器只會把這個前綴保留一段有限時間，而你每送出一個請求就會重設計時器。所以你工作時快取一直是熱的。目前在方案用量內，這個視窗約一小時；在 API 計費或雲端供應商上約五分鐘。子代理在任何方案或 API 上也都是五分鐘，但你可以更改。
[18:01] 有提示快取 TTL 設定，主對話一個、子代理也有對應的一個。但你不一定想這樣做，因為長視窗並非免費：把 token 寫入一小時快取，收費比寫入五分鐘快取高。所以如果你是穩定地連續工作、很少停超過幾分鐘，短視窗通常更便宜，因為你會為從未用到的時間多付錢。長視窗則適合你會離開（開會、午餐、長時間建置）然後回到同一個工作階段的情況。
[18:36] 好，實務上的 TL;DR，這代表什麼、你能做什麼？第一，不要自己破壞快取或想辦法規避：在工作階段開始時、或 clear 之後立刻選好模型與 effort，這樣就沒有快取可損失。
[18:48] 如果你真的要在任務中途換模型，也許先 compact 再換，這樣新模型只需讀一份短摘要，而非整段對話。也要在快取仍熱時 compact，因為 compact 代表模型要再把整段對話讀一次來寫摘要：快取還熱時這次讀取很便宜；若等視窗過了（例如一小時後回來才 compact），同樣的讀取就是全額輸入價。所以要在離開之前 compact，而不是回來時。
[19:20] resume 舊工作階段也是同樣的故事：到那時大多數情況快取已過期（至少我的是，我的工作階段很長，也常休息）。所以回來的第一則訊息會把整段對話再送一次，且完全沒有快取，全是一般輸入。如果你需要完整上下文，沒問題，只有一次；但如果你知道明天要回來，也許離開前先 compact，隔天 resume 的就只是較短的摘要。
[19:53] 另一個讓工作階段內容保持有用的工具是子代理（sub-agent）。有時 Claude 需要研究較大的東西才能回答你，可能是長日誌、整個儲存庫、完整的測試執行，而你其實只想要結論，不想要它為此讀的三十個檔案。這就是子代理的用途：它在自己的上下文中執行，有自己的小型系統提示、你的 CLAUDE.md 與一個任務，所有讀取與工具呼叫都在那邊完成，只把最終結論送回主對話，其餘讀過的都被丟棄。
[20:28] 以 token 來說要講清楚：子代理不是免費的，它仍有自己的輸入與輸出 token、自己的快取（也是那個五分鐘視窗），所以該項工作的總量有時甚至會更高。但你換到的是主對話保持小而精簡、專注在你真正想讓 Claude 做的事，因此之後每一輪都更便宜，你的上下文視窗也不會塞滿這些日誌。
[20:56] 你對子代理有很多控制：可以使用與你工作階段不同的模型（例如用 Haiku 或 Sonnet 子代理去挖資料），可以設定 effort 等級；如果你有自訂子代理，也可以為它們設定模型與 effort 等級。
[21:12] 到目前為止都是關於你自己的工作階段。但如果你是為整個團隊設定 Claude Code 的人，管理端也有同樣的槓桿，一次設定、套用給所有人。大多數在同一處：managed settings（受管理的設定）。這是在管理後台定義的設定檔，團隊中每個安裝在啟動時都會套用，使用者無法覆寫。
[21:36] 可以設定的有幾項。第一是起始模型，以及人們可以選哪些模型。團隊支出意外偏高時，通常追溯到只是把最大的模型留作預設；你可能不需要，也許選較小的模型就好。這只是一行設定，卻是這裡槓桿最高的一項。
[21:56] 第二是起始 effort 等級，故事和前面一樣：人們因為在乎而習慣留在最高，但你不一定需要最高。你可以一次設好預設，需要時仍可為某任務調高；在 Enterprise 方案，還可以為每個模型設定上限。第三是快取視窗（如果你的團隊使用 API 或雲端）：就是前面的提示快取 TTL，可為全團隊一次設定。若開發者習慣穩定連續工作，可維持短視窗；若他們常消失在會議中又回到同一個工作階段，可以設為一小時並接受較高的寫入價格。
[22:33] 你也可以設定允許哪些 MCP 伺服器，避免一堆閒置的伺服器；還有可以發佈到每台機器的組織層級 CLAUDE.md，讓團隊每個工作階段都以它起步。
[22:45] 你也能看到發生了什麼：後台有採用狀況的分析檢視，並在開啟用量點數後有每位使用者、每個模型的支出報告。另一個有用的是 OpenTelemetry：在同一個 managed settings 檔裡用兩個環境變數設定，之後每個安裝都會回報每個人的輸入、輸出、快取讀取與快取寫入。
[23:06] 你可以看到每位使用者的快取讀取佔所有輸入的比例，那應該是壓倒性的最大一塊，因為代表他們的工作階段保持溫熱。若某人的快取 token 占比低，表示他們在某處破壞了快取，如前所述，可能是換模型或換 effort。
[23:24] 你也能看到每個工作階段隨時間的輸入 token：你希望看到一條在任務中上升、但每次 clear 或開新工作階段就掉回來的線；若它只升不降，表示某人活在一個永無止境的工作階段裡，也許在快取已過期時 resume 舊的工作階段。
[23:44] 你也能看每位使用者依模型的成本，這能告訴你誰「什麼都用大模型」。這些就是本場談到的習慣，落到每個人身上，而每一項都只是一則訊息就能提醒：「嘿，我注意到你一直這樣做。」
[23:58] 最後是上限：在 Team 與 Enterprise，席位的五小時與每週視窗就是天花板，沒有人會意外超過。但如果你希望人們能繼續工作，可以開啟用量點數並設定支出上限，可按組織、按群組或按個人。一個相關設定是「達用量上限時自動繼續」：它決定撞到視窗上限的工作階段是單純等待，還是在視窗重置時自動接續任務，這對長時間無人看管的執行很重要。
[24:27] 所以：一個提示是很多個請求，每個請求都帶著整段對話；只要前綴保持不變、你持續往前，快取就讓這段歷史變得便宜。
[24:42] 最終你該記住三件事。第一，在工作階段開始時選好模型、effort 與 MCP 伺服器，然後不要動它們。你可以在使用 Fable 5.1 時更改 effort，但那是唯一不會破壞提示快取的模型。不更動這些設定，每個請求的前面就會與前一個相符，不會破壞提示快取，Claude 可以持續從快取讀取，而不必重新處理整段對話。
[25:10] 第二，要刻意決定放進對話裡的東西：把 Claude 指向你已知的檔案、讓指令輸出保持安靜、把真正吵雜的挖掘交給子代理，這樣只有摘要會回到主對話。
[25:27] 第三，讓工作階段保持專注：開始新任務就 clear，這樣你就不會在做任務三時還在為任務一付費。如果要 compact，請在離開前、快取還熱時做；並記得 resume 舊工作階段或長時間休息、快取過期後回來，就意味著把一切完整讀一次。
[25:49] 模型是所有這一切的乘數，所以請為你的任務選對模型；對團隊來說，這些選擇都能在 managed settings 中做。所以有效率地使用 Claude Code 不代表使用更少 token，而是讓你用掉的 token 都用在你真正要求的事情上。價格與功能會持續變動，但希望這一點不會。
