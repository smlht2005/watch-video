```
[00:01] 我個人認為，使用 AI 最好的方式，是把它當成配對程式設計（pair programming）的夥伴，而不是單純取代寫程式的工具，更糟的是把你的思考外包出去。
[00:19] 我覺得有一種傾向：因為 AI 太令人興奮，你會想把 AI 用在每個地方，想被看成很跟得上 AI 的人，於是產生壓力，覺得「我得提高生產力，這週要交出上百個 PR」，卻幾乎不懂自己在做什麼，靠 vibe coding 做到百萬 ARR 之類。
[00:49] 但我個人看到的是：雖然用 AI 寫程式能省一些時間，我卻發現自己花更多時間在審查 AI 做的東西並修正它。
[01:04] 我也試過很多人說的做法：不要直接叫 AI 把功能做出來，而是先請它寫規格（spec），你審查規格，再進行整件事。
[01:19] 好，我想你們看得到我的畫面吧？（主持人：看得到，沒問題。）
[01:25] 今天對我來說最大的主題是：我一直在用 agent 寫程式，我相信你們很多人也有一樣的經驗——你要如何信任它？
[01:36] 尤其如果你是寫了很多年程式的工程師，你對好的工程有很多看法與累積的教訓；當你看到 agent 在亂猜、產生幻覺，第一百次信心滿滿地宣稱找到了「鐵證」（smoking gun）、其實根本不是真正的問題時，你就失去很多信任。
[02:03] 而當你不太信任你的 agent，我覺得你就沒辦法充分發揮它們的價值。
[02:10] 對我來說，這和管理很像：如果我是一個工程團隊的主管，帶著一票工程師卻不信任他們，我的運作模式就會變成微觀管理——花很多時間在他們背後盯著、檢查他們有沒有做好、有沒有把 bug 送上線。
[02:40] 所以我畫了這張圖——它不是很科學，但這是我想像自己使用 agent 的歷程。
[02:52] 回到大約一年前，沒有多少人用 agent 寫程式，你會處於一個高度介入（in the loop）的模式：只跟一個或少數幾個 agent 互動，一直在試著理解它們在做什麼，盯著每一次輸出、坐在那裡下提示，也無法再平行化，因為你沒有那份信任——你不能在連一個 agent 的輸出都不信任的情況下，叫出一百個 agent。
[03:43] 過去五個月，我覺得自己真的爬上了這條信任曲線。現在我到了一個地步——這聽起來有點可怕，也讓我聽起來像個只會量產 slop（粗製濫造內容）的人，但我保證不是——我的 agent 現在會幫我自動合併（auto-merge）PR。
[04:05] 這說起來很瘋狂，但我今天醒來，有大約 20 個 PR 已經合併進去，我就直接在 main 上審查它們，而且品質都不錯。
[04:18] 我是怎麼走到這一步的？這就是我今天想談的。（中途歡迎提問，Colin。）
[04:44] 我放這張圖不是要炫耀，而是要呈現這段歷程：曲線與我在 Cursor 能合併進去的貢獻量大致呈反向對應。
[05:01] 我五個月前加入，第一個月沒有很多產出，因為我在熟悉程式碼、完全搞不清楚狀況；隨著我對 agent 越來越有信心，生產力才真正拉起來：上個月我交出了一千個 PR（很誇張），這個月才 12 號，我已經合併了將近 800 個。
[05:33] 速度確實很高。我相信你們很多人會質疑這些程式碼到底有多少是好的，這個質疑很合理；但我認為只要把你的 agent 設定得好，你也能達到非常類似的水準，接下來我就談我們怎麼做。
[06:03] 對我來說，和 agent 合作時你工具箱裡最重要的技能是「驗證」（verification）。
[06:18] 我說的驗證，是指 agent 能真的執行程式碼、取得 CPU 追蹤或 heap snapshot、開 iOS 模擬器——不管你的應用程式以什麼方式呈現給使用者，它都能做同樣的事、真正跑起來，實際測試並驗證自己的工作。
[06:45] 因為這才是真正「閉環」的東西：它不保證 agent 寫出好的程式碼，但能讓它至少寫出「正確」的程式碼，這對於能夠信任 agent 是非常大的一步。
[07:02] 我可以分享一個我們在 Cursor 內部的例子：Cursor 的 agent 視窗（agent window）。
[07:31] 這其實是個有趣的故事：我五個月前加入 Cursor 時，原本要加入的是 cloud agents 團隊，但因為我有很多 React 經驗，而 agent 視窗是個 React 應用程式，我就被請去幫忙 agent 視窗的工作。
[08:02] 但當時沒什麼 skill 可以幫我，而 agent 視窗大約一週後就要上線，期限非常緊。我就坐在那裡，打開 Chrome DevTools 的效能面板，自己看追蹤紀錄、試著搞懂那張火焰圖。
[08:23] 請記得，那是我的第一週，我根本不知道自己在看什麼，程式碼對我完全陌生，而我發現我的 agent 也一樣：我把追蹤檔截圖或下載後丟給它，它會說「嗯，看起來像這樣」，信心滿滿地說就是這個東西，我去修，結果發現根本不是真正的原因。這是個非常、非常緩慢的過程。
[08:54] 如果你做過效能調校，或是用 agent 開發卻沒有「驗證 skill」，那你自己就是那個驗證者、就是瓶頸：你叫 agent 去做事，它寫了一些程式碼，你打開本機的 dev build，說「不能動」，再把截圖或 console 錯誤複製貼上，agent 慢慢處理、試著理解、修好，但你始終在迴圈裡當瓶頸，所以根本無法平行化。
[09:34] 所以 control glass skill 是我替 Cursor 做的第一批 skill 之一。順帶一提，glass 是我們內部對 agent 視窗的代號，但它就是 Cursor。
[09:48] 這個 skill 的程式碼本身不太有趣，你的 agent 很容易就能幫你做一個：如果你在做 Electron 應用、網頁應用，甚至 iOS 應用，你可以教 agent 使用 Chrome DevTools 協定，或用 Apple 提供的工具跑模擬器、取得追蹤與做程式化控制，這很有用。
[10:21] 但有一件事我想特別談：這個 skill 帶有一個很獨特的檔案，叫做「功能地圖」（feature map）。
[10:39] 故事是這樣的：我做好這個 skill 後，agent 已經能真的執行 agent 視窗、取得追蹤等等，但它不知道 agent 視窗到底是什麼——有人說「左邊側欄很卡」或「右邊的 PR 分頁壞了」，agent 就像無頭蒼蠅，花很多時間在程式碼裡找「這個功能在哪、要怎麼從 UI 走到它」，等於完全沒用；我在本機跑這個 skill 會啟動 dev build，但它只是空轉、不知道怎麼走到各處，是很糟的體驗。
[11:38] 所以這個功能地圖非常有用：它教 agent 如何到達你所有的功能。在我做的 PStack 外掛裡（Google 搜尋「PStack cursor」就找得到）有一個 create verification skill，會幫你替自己建立這樣的東西，包含功能地圖：它會探索程式碼，建出初版功能地圖，告訴 agent 怎麼走到各種功能。
[12:14] 這非常強大，因為現在使用者回報進來時，你可以把它對應起來，即使是模糊的回報或一張截圖。我們內部在 Cursor 有個 Slack 頻道，很多人針對 agent 視窗與 Grokbot 提供回饋，回報常常品質很差，例如只貼一張截圖然後打「？？？這是什麼」。沒有功能地圖時，agent 毫無頭緒；有了功能地圖，它對如何導覽、如何走到各個功能就有更多脈絡與理解。
[13:03] 例如側邊欄：它是什麼、裡面有哪些子功能、從使用者角度怎麼走到、所有快捷鍵，甚至用 CDP 選取元素用的 DOM 屬性，全都在裡面，對 agent 非常、非常強大。
[13:37] PStack 內附 create verification skill，也有 maintain verification skill，讓你可以保持它是最新的。
[13:46] （主持人：你可以多分享你怎麼做出來的嗎？順便說說 PStack 是什麼，給不熟的人。）
[13:56] PStack 很有意思：首先，名字有點蠢——PStack 的 P 是 potato（馬鈴薯），Potato Stack。因為有位非常有名的 Garry Tan（Y Combinator 的 CEO）做了個叫 GStack（GarryStack）的外掛，有趣的是我們同姓、沒有親戚關係，我覺得很好笑，就調侃 Garry，做了我版本的 PStack，只是針對我自己的一套工程實務去調整。
[14:42] 但老實說我從沒打算做 PStack，它是從一堆 skill 開始的：先有 control glass skill，再有另一個叫 HAL 的 skill，也是從觀察 agent 得來的。
[14:58] 在我剛開始爬這座階梯的早期，我高度介入，對我的 agent 挑剔到極點：我會跟它說「這個功能壞了，這是 bug 回報，為什麼不能動？」而 agent 常常信心滿滿地說「一定是這個，一定是這個東西」。我看它實際的工具呼叫，發現它根本沒有讀我認為會受影響的程式碼，我就極度懷疑，覺得「我不能再信任這個 agent，它完全是在產生幻覺」。
[15:40] 我覺得很容易就這樣累積不信任，並感到無助，不知道怎麼幫 agent 成功。但管理的類比很有用：想像你是工程團隊的主管，你有個很會寫程式的工程師，卻完全沒有業務脈絡，他才剛到職五秒鐘，你要怎麼教他變得有效？方法是透過 skill。
[16:17] skill 就只是 markdown，但它編碼了很多資訊與指示，你可以從 agent 身上引出很多智慧——有些人在 Twitter 上稱之為「把 agent 拉到不同的潛在空間（latent space）」，這是個花俏說法：LLM 是預測下一個 token，當你一開始給它高品質的 token，它就能對應到一個更高、更聰明的空間。這是個很有意思的模型。
[16:59] 我是非常漸進地建起 PStack：從觀察 agent 的各種失敗模式開始，每次看到就說「好，我把它做成一個 skill」，例如「別再產生幻覺，真的去查程式碼、用很多子 agent、不要再猜」。
[17:26] （主持人提問：兩個部分——你如何維護這些 skill？產品會隨時間改變、很多人在動程式碼庫；第二，你怎麼知道你的驗證「夠好」、可以信任這些驗證迴路的輸出？）
[17:56] 我先回答第一個：我怎麼維護這些 skill？如果你不熟這個概念：eval 基本上就是——我的心智模型是——「agent 的單元測試」。你可以自己做 eval，不需要特別的框架，視你想要多科學、多嚴謹而定。
[18:57] 所以 eval 就是用來對 skill 做單元測試的方式。事實上，PStack 在 Potato Mode 之下有一份 playbook 叫 eval playbook，做法相當嚴謹：我會產生很多不同的子 agent，由我的主協調 agent 先針對「我想要這個 skill 做到什麼」訂出評分標準（rubric），再產生所有子 agent，並為它們各自建立目錄，名稱經過巧妙設計，不讓子 agent 知道自己正被評估——因為 agent 其實看得出來，一旦看出來就會改變行為。
[19:49] 總之就是用來測試我正在製作或修改的 skill 是否真的做到我以為它做到的事。Cursor 一個很好的地方是我們支援很多不同的模型，所以你可以跨各種模型去 eval 你的 skill，並了解它在不同矩陣上的表現，尤其是你常用的模型。
[20:21] 我經常這樣做：每次修改 skill 我都會跑一次 eval playbook，確認它真的導向我要的結果。但我要說，維護 skill 其實相當困難，需要很多品味和觀察力：你得很擅長當「後座駕駛」。
[20:47] 就像你做過配對程式設計，看同事寫程式時覺得「你大概可以做得更好，為什麼不這樣做？」你會問同事很多問題；這裡也類似——你不想只是被動的旁觀者，在剛開始建立自己那套 skill 時，你要完全坐在駕駛座上。你當然可以用現成的東西，但如果你要建立自己的 skill，打開所有工具呼叫、讀程式碼、讀 agent 的行為與思考區塊，是看出它們在哪裡失敗的好方法，然後你就可以為此做一個 skill。
[21:36] 至於驗證，怎麼信任它，我覺得也是類似的迭代迴路：我其實也用同樣的流程去驗證「驗證 skill」。
[21:51] eval 有個有趣的地方是你可以「爬山」（hill climb）：你的 eval 可以產生一個分數，你可以讓協調者產生分數，也可以讓另一個模型的「評審 agent」交叉比對，確認第一個模型沒有偏頗（也就是評判所有執行任務的子 agent 的那個模型）。
[22:17] 你也可以爬山：用 Cursor 的 slash loop，說「繼續對這個 eval 跑迴圈，直到全部都是 10 分（滿分）」之類。我對 control skill 用的基本上就是同一種方法，所以其實相當「放手」，我就是這樣做出那個 skill（含其中的 CLI），隨時間它變得非常好；但一開始絕對不順，需要很多迭代。
[22:54] 這裡有個類比——我之後在另一張投影片上也會畫——身為工程師，你現在比較像是主管，或我喜歡的比喻：你像是餐廳的主廚。你不再自己烹調所有食物，你有一組廚師——有線廚（line cook）、有副主廚、有各種工作站——而你的工作是設計環境：你負責佈置廚房、負責把任務分給不同的人。這是很有意思的工作方式，我基本上就是這樣做出這些驗證 skill 的。
[23:50] （主持人追問：假設我們想替某件事建立 eval 或 skill、並讓它自己變好——你是在 work tree 裡隔離、搭配子 agent 與審查 agent 嗎？還是在雲端託管環境？如果我想做，實際的步驟是什麼、從哪開始？）
[24:26] 我覺得最好的起點是本機，因為你可以觀察你的 agent 在做什麼。如果你在為自己建立驗證 skill，我一定從本機開始，叫 agent 把應用程式（CLI、桌面應用或其他）啟動起來，這樣你可以看到它怎麼和應用互動、呼叫哪些 API。
[25:03] 但就我個人而言，我基本上幾乎全押在雲端 agent（cloud agents），因為它們非常強大。Cursor 厲害的地方是：只要花一點時間設定好環境，這些控制 skill、驗證 skill 就會帶來巨大的回報，因為它不只讓你一個工程師更強，而是整個團隊、甚至整間公司都被拉高：你可以開始思考雲端 agent 和自動化流程。
[25:44] 我稍後會再談，但先舉例：我常提到我們有個叫 Benny 的 agent，它會接收所有 bug 回報，自動到雲端開一台桌機、在自己的電腦上跑 Cursor，並用同樣的控制 skill 與應用互動、試著重現 bug 或使用者回報。這非常強大，因為我能立刻自動得到大量資訊：像這個例子，Benny 重現了 bug，但發現其實我們早就修好了，這確認這個問題已經修掉，我只要再發一個 Cursor 版本。這省下我花一小時和 agent 一起確認「到底修好沒」的時間，而且我團隊每個人、公司每個人都受益。
[26:56] 所以我確實認為使用雲端 agent 非常強大。但這是一段旅程：你要先能信任它，才走得到這裡。這回到我這張圖：如果你還在這個區域，我非常鼓勵你不要直接跳到「我要現在叫出一百或上千個雲端 agent」，因為你只會浪費很多 token、而且極其昂貴。
[27:32] （主持人整理：如果我們要走你走過的路，就是從「驗證」開始，做一些 skill 與方法，至少確認 agent 產出的是「正確」的程式碼（好不好是另一個層次的問題）——看 stack trace、看 app 的實際行為；本機信任之後，再思考擴展到雲端、讓更多 agent 自己撿訊號（例如進來的 bug 回報）去解決並回傳 PR；最後一步或許是自動合併 PR——那是你所在的位置，也許不是我想去的地方——然後在 main 上審查它們；這樣對嗎？）
[28:22] 對，沒錯，這就是我畫這條曲線的原因：它描述我的歷程——一開始我幾乎只能用幾個 agent、盯著每一件事。我覺得從這裡到那裡沒有捷徑，因為這是你個人對 agent 的信任程度。身為工程師，你當然不想把程式碼直接塞進正式環境，所以如何建立信任需要很多品味與判斷；不過像 PStack 這樣的外掛確實能幫你更快上手。
[29:05] 如果你信任我、也信任 PStack，那你或許能因此信任你的 agent；但如果你不信任我——我也完全不鼓勵大家盲目信任我——你可以建立你自己那套 skill，看看 PStack、fork 它、做成自己的、改進這些 skill，我非常鼓勵這樣做。
[29:28] 但對我來說，一切都回到「信任」：我們每個人對工程都有不同標準，不同的事在我們的程式碼庫中很重要；當你能把這些全部編碼成 skill、並驗證 agent 真的在照做，你就能爬上這條曲線、開始自動化。
[29:56] 還有一個部分我想談——（主持人：請說，我邊聽邊想更多問題。）這是第三個部分，我還沒談到，也相當有趣：重構與重寫。
[30:08] 這是業界最具爭議的話題之一：你該不該重寫你的應用？工程師很容易這樣想，尤其剛進一家公司，看到程式碼庫就說「天啊這什麼爛東西，誰寫的？太糟了，我想整個重寫」。這是很常見的傾向；在有 agent 之前——甚至可以說現在——大家也都會勸你不要重寫。但我今天想為「你或許該考慮重寫」提出論點，因為這真的視情況而定。
[30:55] Brownfield（既有）應用其實處境不錯，尤其是已經設定得好的。最近我跟一些人聊到，我觀察到一個類比：很多大型科技公司的問題，現在成了每個人的問題。
[31:18] 大型科技公司的問題，例如我在 Meta 時，我們有個巨大的 monorepo、幾萬名工程師在敲鍵盤、交付程式碼；Meta 有很多很棒的工程師，但你可能會驚訝程式碼品質其實沒那麼好。我常開玩笑說：在 AI slop（粗製濫造）之前，我們有人類 slop。

[34:19] 所以我認為程式碼庫一開始就需要非常強的約束：當你有一個可信任、護欄真的能幫助 agent 寫出好程式碼的程式碼庫，你就能走到曲線的這一段——就像我說的，我今天醒來有大約 20 個 PR 被我的 agent 合併。那是因為我投入了非常多時間：我昨天算過，超過 600 個 PR，是我把整個 Grokbot 重構成我一直在建的新架構。

[38:40] 具體在 Grokbot 上：Dune 是我們替 Grokbot 建的架構的有點俏皮的代號。CI 看起來非常惱人，因為每件事都有檢查。如果你寫過 React，你知道最大的陷阱之一是 useEffect，所以在 Dune 與 Grokbot 我們把 useEffect 禁用了。你可以把 Dune 想成「給 Electron 應用的 Next.js」，是為 agent 寫程式而設計的，也針對我們這些由 agent 驅動的應用客製。
[39:30] 所以 CI 的檢查非常具體：像「不准用 useEffect」，被禁用、CI 會失敗並罵你。有些比較有趣、可能讓人挑眉的規則是：我也禁止寫程式碼註解。我發現 99% 的時候，agent 寫的程式碼註解是在描述某些與程式碼完全無關的歷史，例如「Lauren 說你永遠不該做這個」就寫進註解，我心想「什麼？」——我那句話不是什麼持久的全域規則，只是在說「這個 PR 很糟，你該改那一段」。令人意外的是 agent 不太懂這點，或是假設太多、用很蠢的方式做事。所以我們就把所有 agent 做不好的事全禁掉。
[40:33] 一個我們在 agent 視窗很常遇到的例子是效能問題：用過 agent 視窗的人一定遇過效能問題，我們一直在修，但這是永無止境的掙扎，因為合併的 PR 太多，任何一個都可能讓效能、穩定性或可靠性退化。agent 視窗還沒有這個架構，我打算把這些心得帶回去、把那邊整個重構，但它退化得非常頻繁。
[41:08] 舉個例子：我們的行程之間隔離做得很差。在 Electron 裡你有負責渲染 UI 的 renderer 執行緒，也有可執行其他程式、不必阻塞 renderer 的 main 執行緒，但我們沒把這兩者分好，所以常有程式碼不小心被拉到 renderer 執行緒上跑，突然間就和 renderer 搶資源：若要 60 FPS，每一幀要在 16 毫秒內完成，期限非常短；一旦不小心帶進運算量大或大量 IO 的東西，就會非常卡、FPS 掉下來、掉幀，出現超過 16 毫秒的長任務，體驗就變得斷斷續續。
[42:16] 所以我們把做 Electron 應用學到的所有模式編碼進這個框架，變成「硬性失敗」：在 Grokbot 我們真的有個 electron main 目錄、electron renderer 目錄，以及 import CI——會檢查相依圖，確保沒有不小心從一個目錄匯入另一個目錄的程式碼。
[42:42] 這由 CI 強制執行，也由 BugBot（Cursor 的程式碼審查工具，跑在 CI 上）、agents.md 等等強制，無所不在。
[42:55] 我有一段談到：打造好程式碼庫有多個層次。最強的強制層是程式碼庫本身——若架構極度嚴格，開發功能的方式就非常「慣例化」，因為 agent 就是愛複製現有模式。
[43:26] 例如在 Grokbot 我們有「feature（功能）」這個概念，還有 entry points、聊天裡看到的各種卡片，這些都像是框架裡的「名詞」，而建立它們有非常慣例的方式；一個 feature 的所有程式碼都在單一目錄，所有東西共置（co-locate）一處，讓 agent 不必繞來繞去找東西，只要看那個 feature：「好，我在做 Grokbot 的 onboarding 功能，我就在這個目錄工作」。80% 的工作基本上都被封裝在那裡。
[44:14] 它是為「最笨的 agent」而設計，你不必思考。這個框架有個關鍵原則：「最短的路徑就是最好的路徑」，因為這正好契合 agent 愛寫程式的方式——它們愛走捷徑、找最快的方式解決問題，那為何不讓它成為最好的解法呢？
[44:46] 我大概不會講所有細節，這個框架更像是一組想法與原則的集合，而不是會開源的東西；你可以把這張截圖下來、叫你的 agent 也替你做出類似的東西。
[45:08] 重點是「層次」：程式碼庫一層，包含 feature、目錄、封鎖不該被匯入的相依；全部靠靜態分析強制執行，所以有 CI 檢查、很多針對壞模式的 lint、編譯器診斷，也有 BugBot 的規則——那些比較「軟」。前面這些會讓 CI 變紅，所以是硬性約束，agent 不能寫爛程式碼。
[45:51] 至於 BugBot 的規則與 skill，你的 agent 仍然可能忘記、不一定每次都套用，所以我喜歡分層，但不會把它們當成唯一的強制來源，因為它很「軟」。如果你只有規則、BugBot、skill 和程式碼風格指南，不用多久，你的程式碼庫就會變成一團垃圾（抱歉這樣說）。我強烈建議投資在「可以硬性強制」的東西上。
[46:30] 這也是為什麼你選用的技術堆疊也很重要。例如 Rust 又開始非常流行，因為編譯器非常嚴格，會強制很多事、有借用檢查器（borrow checker）要伺候；只要確保你的 agent 不寫 unsafe 區塊，你就能或多或少有信心「能編譯就大概能用、也不錯」，這給你一種信任與信心，讓你作為人類工程師不再需要親自去檢查，你依賴程式碼與靜態分析讓一切順暢很多。
```
