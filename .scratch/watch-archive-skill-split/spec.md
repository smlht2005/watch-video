# watch-archive skill 拆檔後的修正

**Status:** resolved（已實作，待使用者確認後合併）

## Problem Statement

watch-archive skill 原本是一份三萬多字的長文件。長 session 觸發自動壓縮後，每個 skill 的本文只會重新注入開頭約 5,000 tokens，後面的步驟（挑截圖、補充資料、操作 SOP、確認連結、PR）會整段被截掉，agent 就只能憑記憶做這些步驟。

上一次修改把它拆成一份短骨架加九份參考檔，內容幾乎都搬過去了。但 code-review 找出 10 個問題，讓拆檔的效果打了折扣：

- **找不到檔**：專案指示檔、說明文件、腳本印出的提示，用的是只在 skill 資料夾內才成立的相對路徑；從 repo 根目錄照著讀會找不到檔。
- **步驟編號錯或模糊**：現在「步驟編號決定讀哪份參考檔」，WhisperX 的提醒卻把校稿寫成「步驟 4」（應為 3），會把 agent 帶到錯的參考檔；「見步驟 4」則對應到三份檔，要用猜的。
- **掉了一行**：「選參數（沒有把握就用預設）」這行父項沒搬過去，「沒把握就用預設」的指引消失。
- **範本與硬規則衝突**：歸檔指令範本列出強制語言的寫法，卻沒列領域、去語助詞、cue 時間點等旗標，和專案硬規則「不要加 `--lang`」「要指定領域」相牴觸。
- **過時與重複的說明**：骨架裡有一段描述已不存在的舊引用寫法；九份參考檔開頭都寫「編號沿用舊版」，但舊版只剩 git 歷史；骨架的呼叫參數又和參考檔、專案指示檔重複，等於同一條領域規則要改三處。
- **沒有測試保護**：參考檔改名、骨架長回超過上限、路徑失效，現有測試都不會發現。

## Solution

修正拆檔後的文件組，讓 agent 從 repo 根目錄照任何一處指示讀檔都找得到；步驟編號與指向明確、唯一；指令範本符合硬規則；骨架保持精簡、每條規則只有一處權威來源。

同時新增一組測試，直接讀磁碟上真實的文件組，自動守住四件事：
1. 對照表與參考檔一致。
2. 骨架不超過大小上限。
3. 所有對參考檔的引用都能解析。
4. 已知會誤導的寫法不再出現。

## User Stories

1. 身為壓縮後的 agent，我想照骨架對照表讀到每個步驟的完整細節，以便不用憑記憶執行被截斷的步驟。
2. 身為壓縮後的 agent，我想讓骨架小到能被完整重新注入，以便對照表與硬規則一定還在。
3. 身為 agent，我想讓專案指示檔裡每個參考檔路徑都能從 repo 根目錄直接開啟，以便照硬規則讀檔時不會找不到。
4. 身為 agent，我想讓腳本印出的下一步提示（外語影片要寫中譯、混雜語言要手動確認）附上能直接開啟的完整路徑，以便照提示就能讀到對應規則。
5. 身為 agent，我想讓說明文件裡的參考檔路徑寫法一致，以便不必猜哪個是完整路徑、哪個是相對路徑。
6. 身為使用本地 WhisperX 的 agent，我想讓「專有名詞要多留意」的提醒指向校稿步驟（步驟 3），以便校稿時讀到這個提醒。
7. 身為校稿中的 agent，我想讓「穩定的校正先寫進詞典」直接指出是哪份參考檔的哪一節（校正去哪裡），以便不必在三份檔之間猜。
8. 身為不確定該加哪些旗標的 agent，我想看到「沒有把握就用預設」的指引，以便不會擅自加上 `--lang` 或 `--local`。
9. 身為照範本歸檔的 agent，我想讓歸檔指令範本不含強制語言，並列出領域、詞典、去語助詞、cue 時間點、解析度等常用旗標，以便照抄也符合硬規則。
10. 身為維護者，我想讓骨架只描述現況、不提已不存在的舊引用寫法，以便不會有人照舊格式再寫回去。
11. 身為維護者，我想移除參考檔開頭指向舊版的說明，以便文件不依賴只存在 git 歷史裡的內容。
12. 身為維護者，我想讓骨架的呼叫參數只留一句指向參考檔，以便領域規則只在一處權威來源修改。
13. 身為維護者，我想讓專案指示檔只保留領域白名單硬規則、細節指向參考檔，以便三處說法不會不一致。
14. 身為維護者，我想在參考檔被改名或刪除時讓測試失敗，以便對照表不會悄悄指到不存在的檔。
15. 身為維護者，我想在參考檔資料夾多出對照表沒列的檔時讓測試失敗，以便不會有 agent 永遠讀不到的孤兒檔。
16. 身為維護者，我想在骨架超過字數上限時讓測試失敗，以便截斷問題不會悄悄回來。
17. 身為維護者，我想在專案指示檔、說明文件或腳本出現無法解析的參考檔路徑時讓測試失敗，以便失效路徑在合併前被抓到。
18. 身為維護者，我想在參考檔重新出現強制語言的歸檔範本時讓測試失敗，以便與硬規則衝突的範本不會回來。
19. 身為使用者，我想讓拆檔後的所有原有規則仍然存在，以便歸檔品質不因拆檔下降。
20. 身為使用者，我想在修改完成後拿到確認連結，以便在合併前檢查。

## Implementation Decisions

- **模組**：watch-archive 的 skill 骨架、九份參考檔、專案指示檔、說明文件、歸檔腳本的語言提示訊息、三支腳本的說明字串、測試檔。不改歸檔、建報告、挑圖等程式行為。
- **路徑格式**：骨架以外，任何地方提到參考檔一律寫從 repo 根目錄起算的完整路徑（skill 資料夾下的參考檔資料夾）。骨架本身的對照表可以只寫檔名，因為表頭已寫明資料夾。
- **腳本提示**：外語中譯提示與混雜語言提示都改成完整路徑，並指明是「4b」那一節；文字其餘部分不變。
- **步驟編號**：WhisperX 提醒的「步驟 4 校稿」改為「步驟 3 校稿」，並指向校稿參考檔；「見步驟 4」改為指向補內容參考檔的「校正去哪裡」一節。
- **補回遺失行**：在選參數一節的開頭補回「沒有把握就用預設」的指引，作為底下各條的父項。
- **歸檔範本**：拿掉強制語言；列出 `--category`、`--glossary`、`--title`、`--terms`、`--clean-fillers`／`--keep-fillers`、`--timestamps`、`--resolution`、`--keep-media`、`--sop`／`--no-sop`；並註明只有使用者明確指定時才加 `--lang`。
- **刪除過時說明**：骨架中「舊引用寫法都指參考檔」那段，改成只說明對照表如何使用；九份參考檔開頭的「步驟編號沿用舊版」改為不依賴舊版的簡短說明（或直接刪除）。
- **單一權威來源**：
  - 領域判斷的完整規則只在選參數參考檔。
  - 骨架的呼叫參數縮成必要的一兩句加指向。
  - 專案指示檔保留白名單硬規則，細節改指向參考檔。
- **大小上限**：骨架以字元數作為 token 的代理指標，上限 6,000 字元（目前約 4,600），保留成長空間又低於壓縮後每個 skill 約 5,000 tokens 的重新注入上限。
- **相容性**：步驟編號（0–8、4a–4d）維持不變，只修正錯誤引用。

## Testing Decisions

- **好測試的標準**：只檢查外部可觀察的結果（檔案存在、字數、引用可解析、特定寫法不出現），不綁定段落措辭或內部結構，讓日後改寫文字不會誤報。
- **唯一的測試接縫**：磁碟上的 skill 文件組。新增一個測試類別，直接讀 repo 裡真實的骨架、參考檔、專案指示檔、說明文件與腳本原始碼。
- **測試內容**：
  1. 解析骨架對照表列出的參考檔名稱：每個都存在；參考檔資料夾裡沒有表上未列的檔。
  2. 骨架字元數不超過 6,000。
  3. 在專案指示檔、說明文件、腳本原始碼中找出所有指向參考檔的路徑：每個都是從 repo 根目錄起算的完整路徑，且檔案存在；只寫成「`references/…`」開頭、沒有完整前綴的寫法視為失敗。
  4. 參考檔中不出現強制語言（`--lang zh`）的歸檔指令範本。
- **刻意不測**：步驟編號的語意是否正確（例如校稿是否寫成步驟 3）。這類檢查會把測試綁死在文字上，交給人工修正與 code-review。
- **前例**：現有「每個詞典的領域值都在白名單內」的測試，同樣直接讀真實的 repo 檔案做一致性檢查，新測試沿用同一種寫法，放在同一個測試檔。
- **流程**：先寫會失敗的測試（目前第 3、4 項應失敗），再修文件讓它通過；最後跑完整測試套件。

## Out of Scope

- 重新精簡補內容參考檔（4a 挑圖流程）本身的長度。
- 修改歸檔、建報告、挑圖等腳本的實際行為。
- 改流程圖（SVG／PNG）。
- 用真正的 tokenizer 計算 token 數。
- 開 PR 與合併；依專案規則，使用者確認後才進行。

## Further Notes

- 依據：上一個 commit「watch-archive SKILL.md 拆短」的 code-review 共 10 項發現，本 spec 全部採納。
- 先前驗證拆檔時刻意跳過步驟標題行，所以沒抓到遺失的那一行。新測試不做逐行比對（舊版已不存在），改用上述四項持續守護。
- 官方文件說明：壓縮後每個已呼叫 skill 本文最多重新注入 5,000 tokens、合計 25,000 tokens，從檔案開頭保留。
