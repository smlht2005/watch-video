# 字幕 OCR：偵測（det）成為新瓶頸，每張約 3.3 秒，比單獨實測的 1.8 秒慢

Status: needs-info
Branch: 從最新 main 開新 `claude/...`

## 背景

`subtitle_ocr.py` 改用 PP-OCRv5 mobile 辨識後（PR 內），辨識 `rec` 只剩約 0.5 秒，**偵測 `det` 變成大頭**。第 097 集全片實測（接電源，Idle 優先權，`--workers 1 --every 3`，8 段共約 80 分鐘）：

| 項目 | 數值 |
|---|---|
| 每張平均 | 3.9–4.5 秒 |
| 偵測 `det` | 3.0–3.9 秒（約八成） |
| 辨識 `rec` | 0.5–0.6 秒 |
| 其餘 | 0.1–0.4 秒 |
| 畫面 | 1 個文字框，1050×130 px |

而同一批畫面先前單獨實測（前景、機器較閒）偵測只有約 1.8 秒，所以 3.3 秒很可能受 Idle 優先權、混合核心（P／E 核心）或其他程式影響。

## 要查的事（只調查，不一定要改）

1. 偵測為何比單獨實測慢近一倍？對照：`--low-priority` 開／關、前景／背景、`--workers 1／2`，各跑同一段 20 張，看 `[trace]` 的 `det`。
2. 偵測對一張只有 1 行字的 1050×130 圖片要 3 秒是否合理？RapidOCR 偵測預設會把圖放大到 `max_side_len`；這種又寬又扁的字幕列，是否可先裁成更小或固定尺寸再偵測？
3. 能否不偵測：字幕位置固定（單行、固定高度），可評估跳過偵測、直接把整條字幕列送辨識（要確認多行字幕與兩行換頁時的準確度）。
4. 評估 PP-OCRv5 mobile 偵測模型（`twmht/ppocr_v5_mobile/det.onnx`，4.8 MB）：速度與準確度（第104集那 10 張誤判畫面）。
5. `onnxruntime` 的執行緒數：第 097 集實測 2／4／預設都約同樣速度（機器空閒時），已拿掉 `--threads`；若偵測在負載下才慢，可再試。

## 驗收

- 找出 `det` 變慢的原因，寫在本 issue 的 Comments。
- 若有更快且準確度不降的做法，另開 ticket 實作；沒有就維持現狀並寫明理由。
